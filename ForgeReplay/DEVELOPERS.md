# ForgeReplay developer notes

Layering: `Core/` has no game or Unity reference (format, later timeline, scoring, statistics); `Native/` holds the game hooks. It depends on ForgeCore (`Level.TryCurrentLevel`, `Level.Fingerprint`, `InstalledPlugins`, `SoloDrop`, `ChunkLog`, `Compact`) and BepInExPack_GTFO. It is built on its own, not through `Forge.Architecture.sln`:
`dotnet build Mods/ForgeReplay/ForgeReplay.csproj -c Release --disable-build-servers -m:1 -p:GTFOBepInExPath=<profile>/BepInEx`; offline tests: `dotnet run --project Mods/ForgeReplay/tests/Core/ReplayCore.csproj -c Release`.
Package: `python Mods/ForgeReplay/tools/package_release.py --artifacts-path <dotnet artifacts> --output <folder>` writes `NAinfini-ForgeReplay-<version>.zip` (`manifest.json`, `icon.png`, `README.md`, `CHANGELOG.md`, `LICENSE`, `ForgeReplay.dll` from the Release output, `lang/en.forge`, `lang/zh.forge`); it refuses when the manifest's dependencies are not exactly BepInExPack_GTFO 3.2.4, GTFO_API 0.6.1 and ForgeCore at its own manifest's version, when `ForgeReplay.csproj`'s `Version` differs from the manifest, or when the two language files hold different keys. Identical inputs give identical bytes; it never publishes or installs. Put the zip beside the ForgeCore zip and run `python Mods/Build/verify_release.py --packages <folder> --artifacts-path <dotnet artifacts>` to check the DLLs against the build and the assembly versions against the manifests.

## File

`replay/<yyyyMMdd-HHmmss>_<rundownId>-<tier letter><level number>.frpl` beside the game exe, a ForgeCore `ChunkLog` whose format version is `ReplayHeader.FormatVersion` (9; a recording of another version is listed as not supported). Chunk type 0 is the header, written when the level is built, before anyone lands. Chunk type 3 is the footer (below), the last chunk of a finished recording; a recording that was cut short has none and the list reads it through once instead.

## Header (chunk type 0)

Variable-length integers are ForgeCore `Compact` (signed ones zig-zag); text is a count then UTF-8 bytes; a list is a count then its items. In order: replay version (text); game revision (`CellBuildData.GetRevision`, signed); plugins (list of GUID, version, DLL SHA-256, all text; ForgeCore is among them); rundown ID (unsigned); tier (signed, 1 = A); level index (signed, zero-based); build seed, host-ID seed, session seed (signed); generation hash (text, one hash over every section); generation sections (list of name, hash: `native`, `zones`, `areas`, `doors`, `terminals`, `containers`, `generators`, `items`, `enemies`); recorder name (text); recorder slot (signed, the character slot 0 to 3 of the recorder: every lookup of the recorder among the players uses it, never the name, which two players may share); recorder is host (1 byte); start mode (1 byte, 0 launch, 1 mid-join: a client whose level is built while the game says it is dropping in, `SNet.IsInDropin`); players (list of slot signed, name text, loadout text: the gear JSON of the standard, special, melee and tool slots, one per line, an empty line for an empty slot; one entry per occupied character slot 0 to 3 read through `SNet.Slots.GetPlayerInSlot`, people and bots alike, so a bot is listed under its own name without a mark and whether `SNet.LobbyPlayers` holds bots does not matter); then, only when there are any, the content section: a count (never 0) of package directory name text and content hash text, ForgeCore `InstalledPlugins.ContentPrints` (one `Fingerprint.OfFolder` per `plugins/<package>/forge` folder: relative path and length of every file, and the content hash of each file up to 1 MiB; read on a worker thread started at plugin load, `Session.PrepareContent`). `ContentDifference` names the packages missing here or with other files, the list's details show it and a replay notes each in `Skipped`. Nothing may follow the last field. The header ends with the rundown's name (text, read from the rundown block's title when the level is built): a header without it is refused as the rest of an unreadable layout; `Native/RundownNames.cs` names the rundown from the loaded block, the official IDs (R1 to R8) or another recording when the text is empty.

## Footer (chunk type 3, `RunSummary`)

Written when the recording ends, so the replay list shows a finished recording without reading it. Outcome (1 byte: 1 success, 2 failed, 3 left), duration in ms (unsigned), start and end as UTC milliseconds since 1970 (signed), the player count (unsigned, 4), then per slot 0 to 3: rays, ray hits, kills, downs, revives, packs (unsigned) and bullet, melee, explosion damage and damage taken, each x10 (unsigned). The counts are `Analysis` fed live in its totals-only mode (host flag and recorder slot from the header): `Rec.Emit` passes every event of those kinds to `PlayerRecorder.Count`, the same `Analysis.Take` that a full read of the file uses, and a Core test checks both agree. On a client recording the footer's kills and damage are only what this machine saw; the list takes a client recording's kills and downs of the other players from a background read (`ReplayList` Totals), not from the footer. After the players, a completeness block: U lost samples, U lost events, U failed recording hooks (Rec.Fail calls), U deepest write queue, eight U frame counts of the recording frames (upper edges 8, 12, 17, 25, 34, 50, 100 ms, then over 100), U frames over 100 ms (hitches), U how many of them follow (at most 16), each U moment in ms and U frame ms (RecordingHealth; PlayerRecorder.Tick times its own frames, BlockPipeline.MaxQueue and LostSamples). The format version stays. Nothing may follow the last field.

## Run report (Core/RunReport.cs)

Everything the statistics pages, the list's summary and StatsExport read beyond the counts is worked out offline in the one pass of Analysis.Run (Analysis.Report; nothing is added to the recording path, the footer or TotalsOnly): friendly fire (PlayerHurt's attacking player, a ray that ended on a player; a slot without PlayerHurt events of its own is HurtKnown false and shows —), downs (the damage in the three seconds before, or a grab by trap, tank or snatcher; a client's cause comes from ClientInference.Hurts and is marked Estimated; the time down, the rescue and the reviver from ReviveBy), damage settles once: `Analysis.Damages` holds one `DamageLine` per bullet, melee or explosion hit (the weapon wielded or the sentry's bullet row, the recorded or estimated damage, the hit's own time; a reading the game did not sync settles at the hit and is capped by the enemy's full health), and both the per-player StatDelta rows and the weapon page add from those lines, so the totals and the weapon rows always agree; weapons (by what the player wielded; mines and a sentry's bullets are their own rows, the sentry split being a bullet hit beside a SentryShot of the owner's sentry with no ray of the owner then, so an estimate; aim share only for the recorder, whose aim transitions (108) carry it), enemy types (appearances, kills, enemies that went away, mean seconds from the first hit to the death, mean hit distance, overkill waste), ammunition and supplies (PlayerStatus pools, Supply events, ClientInference.Packs for health, ammunition and infection restored), tension (enemies hunting each second of the world state), zones (PlayerPlace), doors, scans, terminals, objectives, waves (Wave start and end; spawned and died in the window, damage and downs, cut at WaveCapMs when no end came), joins, leaves, checkpoint reloads, sentries, mines and foam per owner, and health, infection and stamina curves. The timeline does not report EnemySpawn, so an enemy is first seen at its first sample, hit or end. Resource boxes: the game's box state packet (pResourceContainerItemState) holds only status, so who opened one is the nearest player at that moment, worked out (BoxesOpened); who picks a pack up is exact (the pack in PlayerKit appearing). ReportJson writes it all as the report object of `<recording>.stats.forge` (JSON; `schema` 1 first, then the level, players, kills, highlights, `notes` and `report`), with an estimated flag or list beside every worked-out value.
- Wake causes in a client recording are worked out, not read (it has no host wake, hit or enemy-health records): `WakeCause` is Unknown, Sensed, Noise, Damage, Passed (a neighbour woke it), Door (a weak door broke), Explosion or Sentry, and the feed names the source only when the recording can say it, never a guess. A sentry hit is matched in `HitMatch` along the sentry's aim line (within 1.5 m across it, or inside a 15 degree cone up to 40 m), because a sentry's bullets fly at its target while the recorded aim lags behind. `EnemyHealthTrack` gives the selected enemy's health: the maximum from the full-health table, the exact current value from EnemyHealth records, otherwise an estimate from the state byte of the pose samples (health in bits 2 and up, 0 to 31), shown as about N.

The screen: the statistics panel has six pages (team, rating, weapons, enemies, supplies, level; ReplayScreen.Pages.cs, each a ForgeUI `HudTable`, with the rating page drawn as cards, a radar and a comparison table), the time bar carries only downs, wipes, waves, scans, alarms, the reactor, checkpoints, kills worth a mark, pings (3 s repeats by one player merged) and the highlights, and the kill feed has down and revive lines. A card shows the recorder's magazine and stamina (not boosters).

## Public control and scripted runs (`Native/ReplayControl.cs`)

The release DLL holds no development switch, readback or per-frame development code, and there is no separate development plugin. `ForgeReplay.ReplayControl` is the public interface to the list and the screen, what a player does with the mouse: `List()`, `OpenList()`, `ListView(section, rundown, file, page)`, `Play(file = "latest")`, `State()`, `Jump(ms)`, `Pause()`, `Resume()`, `View(mode)` (Free, Follow, Eye, Overhead, Orbit), `Auto(on|off|state)`, `HighlightList(n)` (opens the panel; n from 1 also clicks that row), `Assist(fog|brightness, on|off|<level>|state)` (the fog-clearing and global-brightness switches; the answer line carries the fog the volume draws), `DamageNumbers(on|off|state)` (a scripted switch only; a player always has them), `Film(mark|play|stop|clear|state)`, `ExportStats(file)`, `Disk(limitMb)` (reads used bytes, limit and keep count; a number first sets the limit for the run), `Prune()` `Recordings()` (the readable recordings as `RecordingInfo[]` for another mod) and `Exit()`, each returning one line (the table in `Docs/forge-replay/PLAN.md` §3). `ForgeReplay.ReplayEvents` is what other mods hear: `RecordingFinished(RecordingInfo)` when a recording is closed (path, rundown name, level code, `Outcome`, duration ms, complete, starred; not raised for a file cut off by a crash) and `OnNote(ReplayNote)` as playback passes a note (time ms, mod id, kind, payload, mark; a jump passes nothing). A mod writes a note with ForgeCore `Recording.Note(modId, kind, payload, mark)` and needs no reference to ForgeReplay: the recorder writes event 101 (Text mod id, Text kind, Text payload up to 1024 bytes, U mark) on host and client alike; marked notes show on the timeline and in the event list and every note is in the exported statistics `notes`. `ReplayProbe` (`Held()`: per recorded slot what the body holds against the recording; `TraceStart()` / `TraceStop()`: the sound events posted in between, replay and game told apart) is read-only, has no switch and no per-frame code, and runs only when called. A script calls them by name through ForgeDevelopment's drive: `python Mods/ForgeDevelopment/tools/drive_cli.py --session <session.forge> call static:ForgeReplay.ReplayControl Play latest --until State playing`. Everything else a test needs is ForgeDevelopment's own: entering a level with bots (`run-drive-session.py start`, `drop`), a seeded solo start (`call static:ForgeDevelopment.Native.SeededDrop Start 37-B1 "1,2,3" 3`), a fight and a round of level interactions (`call static:ForgeDevelopment.Native.LevelScenario Start --until State finished`; it leaves the level at the end, so the recording gets its footer, unless started with `true`), screenshots, native field reads, logs, quitting, and frame time and allocation (`run-drive-session.py start --perf`, read with `Mods/ForgeDevelopment/tools/analyze_performance.py`). A recording is read back outside the game: `REPLAY_FILE=<file.frpl> dotnet ForgeReplay.Core.Tests.dll` (from `tests/Core`) prints the whole header as one `header-json` line (level, seeds, players, generation sections, plugins), the event counts by kind, the footer and the cut-file check.


## Recorded (data chunks)

Samples (position in metres, rotation, one state byte below 128):
- Players, entity = slot 0 to 3, state = health 0..127. `PlayerRecorder` polls `PlayerManager.PlayerAgentsInLevel`: the recorder's own player every frame, the others at most every 33 ms.
- Enemies, entity = 4 + the slot of ForgeCore `Enemies.Live` (at most 1024), state = alert (`EnemyAlert`, low 2 bits) + health in 32 steps (`<< 2`). `EnemyRecorder` samples each enemy on its own clock: every 50 ms while it hunts, 100 ms awake, 1000 ms asleep (spread over the second); `EnemyRecorder.Hot` (a hit, a wake-up call, a sleeper sensing someone) samples it on the next tick and at the awake rate for 2 s, so a sleeper that is moved or woken is recorded within a frame or two and a sleeper nothing touches is read once a second. The alert is read through `Enemies.Alert(alive, ai, locomotion)` from the AI and locomotion kept at the enemy's spawn; the list is compared with ForgeCore's only when `Enemies.Version` moves (an enemy that dies leaves it at its death); values fixed at spawn (data block, dimension, health, size, seed) are kept for every keyframe. An unchanged sample is not written.

Blocks: about two seconds each, compressed by ForgeCore `ChunkLog` (Brotli). The first block of a recording is a keyframe block (every entity and remembered object state written in full), then one every 30 seconds; a checkpoint reload (`GameEvents.CheckpointReloaded`, after its Checkpoint event) makes the next frame cut a keyframe block at once (`BlockPipeline.KeyframeNext`) and the 30-second rhythm restarts from it. A jump decodes from the keyframe before it, at most 30 seconds of blocks.

Records in a block body (`Core/SampleCodec.cs`), each a kind byte, then U milliseconds since the previous record (the block start for the first):
- Event (kind 2): U16 type, U payload length, payload.
- Sample (kind 1, 3 or 4): U entity, a byte `absolute | state << 1`, the position in centimetres (three S: absolute for the entity's first sample in a keyframe block or after it left, else the difference from its last written position), then the rotation. Kind 1 writes the 6-byte smallest-three quaternion (ForgeCore `Compact.WriteQuaternion`); kind 3 writes nothing (the same 6 bytes as the entity's last written sample); kind 4 (same largest component, and shorter than 6 bytes) writes three S, the differences of the three packed 15-bit components from the last written ones. All three give back the same quaternion bytes, so the rotation is exactly what kind 1 holds. An absolute sample is always kind 1.

Events (payload = Compact varints: U unsigned, S signed, Pos = three S in centimetres, Text = U byte count then UTF-8, at most 200 bytes except the Presence loadout; a payload holds at most `PayloadWriter.Capacity`, 8192 bytes, and a text is cut to what is left of it). The type numbers are `EventKind`.
- 1 EnemySpawn: U entity, U enemy data block id, U dimension, Pos. Also written for every living enemy at the start of each keyframe block.
- 2 EnemyGone: U entity, U died (1 killed, 0 despawned).
- 3 EnemyHurt: U entity, U kind (0 bullet, 1 melee, 2 explosion), U damage x10 (what the hit came with), U attacker slot (255 none), U limb id, U settled (1: the game settled it on this machine, written after `ProcessReceivedDamage` from the health before and after; 0: a client's reading of its own hit at the limb), U health taken x10, U lethal, U overkill x10 (damage past the last health), U limb type (0 normal, 1 weak spot, 2 armour), U limb multiplier x100 (`m_weakspotDamageMulti` / `m_armorDamageMulti`), U in the back (the limb's `ApplyDamageFromBehindBonus` above 1, for bullets that allow it and for swings), U gear category id, U distance from the attacker x100. A client's reading has taken, lethal and overkill 0.
- 4 EnemyLimb: U entity, U limb id (a custom limb was destroyed).
- 10 PlayerStatus: U slot, then U locomotion state (`PLOC_State`), wielded slot, infection percent, standard, special and class ammo in the pack, U down (1 while downed). Written when any changed; every keyframe block writes it for each player.
- 54 PlayerMotion: U slot, S forward, S right: the walk values the game gives the player's animator (`PlayerLocomotion.m_animVelFwd`, `m_animVelRight`, in steps of 0.05 m/s). Checked every 50 ms, the rate the game's own network sends them at, written when they changed; every keyframe block writes it for each player. A jump restores it, and it is not reported as a one-shot event.
- 11 Shot (one per ray, so one per shotgun pellet): U slot, U weapon key (the gun's archetype data block id), Pos origin, Pos end, U hit, then U what the ray hit (1 level geometry, 2 an enemy limb, 3 a player). `hit` is only the ray ending on a collider: a hit in the statistics is kind 2. A remote human's ray on this machine is a local picture cast for its look; `BulletWeaponSynced.Fire` deals damage only for bots.
- 12 Melee: U slot, U kind (0 light, 1 heavy, 2 push), U 1 decided. Own: `MWS_AttackLight.Enter` is the press; `Hooks.Melee.Settle` (every recorder frame) writes the light swing when the button is up first or the state moves on to anything but the charge, and nothing when `MWS_ChargeUp` starts (then 63 MeleeCharge 1 at once, and heavy at `MWS_AttackHeavy.Enter`). Remote: the fire flag of `MeleeWeaponThirdPerson.ReceiveClassItemSync` turning on, heavy when the weapon was charging. A decided swing plays at once on the puppet. The first-person view enters the game's light state at a light swing and its charge state at the charge (`FirstPerson.Charge`, the fire button held through ForgeCore `InputLease` so the charge state does not let go), the release at heavy and `CancelChargeToIdle` for a charge that ends without one.
- 13 PlayerHurt: U slot, U kind (0 bullet, 1 melee, 2 explosion, 3 tongue, 4 projectile, 5 fall, 6 anything else), U damage x10 (the amount `OnIncomingDamage` applies, modifiers included), U attacker (enemy entity + 1, 0 not an enemy), U attacking player (slot + 1, 0 none). Written from ForgeCore `PlayerHits.Watch`, the one path every hit takes, on the machine that settles it: the recorder's own player and, on the host, the bots. The kind comes from the receive method around it (`GameHooks.PlayerReceived`, which covers the base methods and the six `Dam_PlayerDamageLocal` overrides that do not call base).
- 14 Revive: U slot. 15 Pack: U slot, U item id.
- 55 PlayerKit: U slot, U pack item id, U pack uses left (`GetBulletsInPack(ResourcePackRel)`), U consumable item id, U consumable count (`CurrentConsumable`), U carried item id (`InLevelCarry`), U flashlight on, U pocket item count, then that many item ids. Item ids are `ItemDataBlock` ids, 0 none. Polled every 250 ms, written when it changed and again in every keyframe block. A replay reads `WorldState.PlayerKits[slot]` (`Core/PlayerKit.cs`), names through `Native/ItemNames.Name(id)`. The guns and the tool are the loadout: `ReplayFeed.Holder`, `GearName`; the held one is PlayerStatus's wielded slot. The gear is compared with what the file last said every 2 s and a changed one is a new Presence line.
- 56 ReviveBy: U target slot, U reviver slot (`AgentReplicatedActions.DoPlayerRevive`, runs on every machine with both names). 57 Supply: U giver slot, U receiver slot, U kind (0 health, 1 ammunition, 2 disinfection; `PlayerAgent.GiveHealth`, `GiveAmmoRel`, `GiveDisinfection`, on the giver's machine: the recorder's gifts and, on the host, the bots').
- 58 Objective (state, key = layer: 0 main, 1 secondary, 2 overload): value `eWardenObjectiveStatus`, extra sub status x 256 + chain index, Pos 0. Polled every 500 ms (another package patches the game's state change). 59 Disinfection (state, value `eDisinfectionStationStatus`).
- State events are remembered per object and written again at the start of each keyframe block: 20 Door, 21 Scan, 22 Puzzle (chained puzzle / alarm), 25 Generator, 27 ItemState (pickup state), each U object key (the Unity instance id zig-zagged, `Rec.Key`), U state, U extra (scan progress percent), Pos. ItemState continues with U holder slot + 1, U ammunition or uses x 100, U on the floor, U in a machine, and a second Pos: where the recording first saw the item, which is where the level had it (the first state of a level item comes before anything moves it); a replay that jumps looks for the level's own object around that place and puts it back. Weak doors destroyed by enemies replay through the game's own destroyed-door handler (the door is gone and its sound stops), and a replay that starts mid-run silences the loop sounds of scans, chained puzzles and alarms that are not running at that moment (ForgeCore `WorldStates`).
- 23 Wave: U started, U wave id. 24 Terminal: U object key, Pos, Text command line. 26 ItemSpawn: U item id, Pos, U item mode (the game's ItemMode number: 0 first person, 1 third person, 2 pickup, 3 instance). 28 Checkpoint: U 0 reached / 1 reloaded. 29 Chat: U sender slot (255 unknown), Text.

More events (`Native/HooksMore.cs`; state ones are remembered per object and written again at every keyframe block, like the ones above):
- 30 Interact: U slot, U type (`pGenericInteractAnimation`: place mine, pick up, point, give or use a resource, shove, reload). 31 Throw: U slot, U status (1 charging, 2 thrown).
- 32 Sentry (state): U object key, U 0 standing / 1 gone, U owner slot + 1, Pos, then Pos rotation (Euler degrees), U 0, Text the sentry's own gear JSON (playback builds that gear). 33 SentryShot: U gun key, Pos, then U the sentry's state key, Pos muzzle direction, then U the gun's `WeaponAudioDataBlock` id (0 unknown) and U its `eWeaponFireMode` (10 semi, 11 auto, 12 burst, 13 shotgun semi); playback posts every entry of the block's `eventOnSyncedAutoFirePerShot3D` / `eventOnSyncedBurstFirePerShot3D` / `eventOnSemiFire3D` list at the muzzle (the body, mechanics and tail layers, as `BulletWeaponSynced.Fire` does), a burst gun whose block does not ask for a sound per shot once per 400 ms, and for a shot recorded without them takes the two from the sentry's recorded gear JSON (its `AudioSetting` and `FireMode` gear parts, which the game sets the sentry's firing up with), else, for a recording without that gear, from the replay's own sentry of that model, and plays nothing when neither has one. The format version stays (appended fields). 34 Mine (state): as Sentry, 0 placed / 1 triggered / 2 picked up, the last U its item data block. 35 Explosion: U kind (0 explosive mine, 1 foam mine), Pos, then on newer files, for a mine, U most damage x 10, U least x 10, U near x 10, U far x 10 (the mine's `m_damageMax`, `m_damageMin`, `m_distanceMin`, `m_distanceMax`, prefab values; appended, the format version stays). 60 Music (state, key 0): value `MUS_State`, polled with the objectives. 61 Foam (state, key sync id): U phase (0 flying, 1 landed, 2 gone), U volume x 1000, Pos, Pos velocity, U expand volume x 1000, U scale x 1000, U strength x 1000, U allow splat, U owner slot + 1 (`ProjectileManager` DoFireGlue, DoSpawnGlue*, DoMergeGlue, DoDestroyGlue). 21 Scan's extra: percent, bits 8-11 the slots inside, bits 12-15 how many it needs.
- 36 Tongue: U enemy entity, U phase (2 launched: `Attack(Agent)` / `Attack(Vector3)`, then after the target U which of the enemy's tentacles in their order under it; 0 out: `OnAttackIsOut`; 1 back: `AttackIn`, the retract starting; `OnAttackIsIn` is not hooked because the game folds its empty body with `DeAllocateGPUCurvy`), Pos (world: the target's place or the fixed place), U target (slot + 1, 0 a place). 37 Projectile: U kind (0 aimed projectile fired, 1 foam fired, 2 foam destroyed, 3 an aimed projectile in flight, 4 its flight ended: gone from the list, inactive, or standing still since the last sample, since a projectile that hit lingers there about five seconds; it is not written again while it lingers), U id (foam: sync id; 3 and 4: the projectile's instance id), Pos; a flight sample (every enemy sample, `ProjectileManager.m_projectiles`) then has U ProjectileType + 1 (0 not known; read from the prefab name its copy has) and Pos its direction. Playback draws each flight as the game's own projectile (`Flights`, ForgeVisual `ProjectileLooks`; a flight sample that did not move ends the flight) and starts the puppet's own tentacle at a launch (`Puppeteer.EnemyTongue`; a recording without launches starts it when it is out). 48 WeaponSound's name is the per-shot 3D event of the weapon's fire mode (`WeaponAudioDataBlock`: semi fire, else the synced burst or automatic per-shot event). 38 Scream: U entity, U kind (0 scream, 1 scout scream), then U animation index. 39 Scout: U entity, U feelers out.
- 40 Noise: U source slot (255 none), U type (`NM_NoiseType`), Pos, U largest radius x10. 41 Ping: U slot, Pos.
- 42 ResourceBox (state): `eResourceContainerStatus`. 43 Reactor (state): `eReactorStatus`, extra = progress percent. 44 Environment (state, key 0): U key, U fog data block id of the reality dimension, U light sequence section count, Pos of the sequence.
- 45 Presence: U slot, U 1 joined / 0 left, then Text the player's name and Text the loadout (the header's gear JSON lines, up to the payload size), so a player who joins after the header still has a name and gear. 46 HostChanged: U new host id, U 1 when the recorder is now the host; the analysis counts by the host's rules from there on. The first block after a reload or a recall (host migration, joining a level in progress) has settled is a keyframe. 47 GameLog: U `eGameEventChatLogType`, Text.
- 48 WeaponSound (state, key = the Shot's weapon key): Text = the first Wwise event name of the weapon's per-shot 3D list (its body layer), written with the weapon's first shot so a replay can play it without owning the weapon; then U muzzle flash class (0 rifle, 1 pistol, 2 shotgun, 3 submachine gun). Playback posts the whole list of the `WeaponAudioDataBlock` that holds that name (`Deployables.ShotList`) at the muzzle, once per shooter and millisecond (a shotgun's pellets sound once), the name alone when no block holds it; one concrete hit sound per shooter and millisecond.
- 53 Wake: U enemy entity, U propagated (1 when another enemy's wake-up passed it on, 0 when the enemy itself noticed someone), U distance x10 (metres from what woke it), U delay in ms, U propagator (the enemy entity + 1 whose `EnemyAgent.PropagateTargetLimited` / `Full` handed this enemy its target through `EnemyAI.InjectPropagatedTarget`; 0 none), then (since 11-06; a reader checks `AtEnd`) the cause the game names: U the target's `AgentTargetDetectionType` (2 sensed while asleep, 3 ability, 4 damage, 5 passed on; 255 no target), U 1 when it woke on a noise it heard (`EB_Hibernating.OnNoiseDetected`), U the player it woke for, slot + 1 (the target's agent, or the noise's maker; 0 not a player), U the target's `Agent.NoiseType` (what that player was doing). - 49 EnemyAttack: U entity, U attack state (`ES_StateEnum`: strikers, tanks, shooters), U animation index, Pos aim, U wind-up and attack time in ms. 50 EnemyHit: U entity, U reaction type (`ES_HitreactType`), U impact side (`ImpactDirection`), U animation index. 51 EnemyState: U entity, U locomotion state (`ES_StateEnum`), written when it changes and at every keyframe block (kept per entity in `WorldState.EnemyLocomotion`). 52 Reload: U slot (the local player's reload animation starts).

**Host records wire format (Core/HostLink.cs, Native/HostSync.cs).** One ForgeCore `Net` channel (`NAinfini.ForgeReplay`), content `frpl-<recording format>`, one reliable byte message `records` (`channel.Bytes`, version `HostLink.Version` = 3, at most 1000 bytes, under the 1 KiB ForgeCore sends as one message), broadcast by the host and taken only from the host. ForgeCore carries it only between players whose copies match, in the order sent and each once, and drops a packet sent before a checkpoint reload or a host change; the host follows each of those (`Net.WorldChanged`), every newly matching client (`PeerSynced`) and every 20 s with a snapshot. A packet: type byte 0x48, then records. Hit (type 1): byte `kind | slot<<2 | limbType<<4 | lethal<<6 | behind<<7`, enemy `GlobalID` (u16 LE), varints taken x10, offset ms, gear category, distance cm. Wake (2): enemy id (u16), flags (propagated, heard, detection<<2, hasPropagator<<5), byte `player | action<<3`, optional propagator id (u16), varint offset. Snapshot (3): slot mask byte, then ten varints per slot (packs applied and supplies received are the last two). Hurt (4): slot byte, byte `kind | (fromPlayer + 1)<<3` (0 none), attacking enemy `GlobalID` (u16), varints damage x10, offset ms. Supply (5): giver, receiver and kind bytes, varint offset. Pack (6): slot byte, varint offset. Ray (7): byte `slot | hit<<2`, varint offset. The offset is ms after the packet's first record; the receiver turns it into an age before the last record. A packet with anything cut off or out of range is refused whole (`Net.Drop("replay-sync-malformed")`).

**Format changes.** A change playback or the statistics cannot read raises `ReplayHeader.FormatVersion` and a recording of another version is refused: nothing reads or converts an older format, and the list shows it as another format without deleting it. Version 5 added the settled fields of EnemyHurt and the two health syncs; 6 takes each data block hash over the game's own CellJSON text of the block; 7 writes two-second Brotli blocks, a keyframe every 30 seconds and the rotation kinds 3 and 4, with ForgeCore's unambiguous fingerprint encoding; 8 makes every payload the full current layout and drops the readers' end-of-payload fallbacks; 9 keeps the same layout and adds 108 PlayerAim (107, the per-frame eye, is retired: an old file's 107 is ignored as an unknown event). Readers ignore event types they do not know.

Hooks are in `Native/Hooks.cs`, `Native/HooksMore.cs` and `Native/HooksWorld.cs`, each feature put on separately so a missing game method costs that feature only: a Harmony class for a method only ForgeReplay patches, a subscription to `ForgeCore.GameHooks` for a method other packages patch too (ForgeCore patches it once). Not recorded: reload progress and tool use beyond the animation start (`Interact`), scout details beyond screams and feelers, other players' magazines, aim and stamina (the game does not send them), sentry idle aim, hacking and map use, the objective's main text and progression, lightning, drama tension, screen effects and ambient sound. Noise made by a remote player is written when it arrives (`ReceiveNoise`), the local player's when it is made (`MakeNoise`).

## Playback presentation

`Native/Playback/EventPresenter.cs` turns the events the timeline passes into what the game shows and plays: `Present(record, state, speed)` per passed event, sound through `ReplaySounds` (`AudioKit.PostGameEvent`, remembered so that `StopAll` can stop them at a jump) tiered by `PlaybackClock.Tier` (everything up to 2x, key events up to 4x, none above), effects always. Per event: a shot (tracer from `Fx.Tracer`, muzzle flash, impact effect, the recorded weapon sound), swings, revives, pings, enemy hurt, death and scream voices, tongues, aimed and foam projectiles, mine explosions (the game's effect `FX_Tripmine` / `FX_TripmineGlue`), a wave start, a terminal command, a hurt player, and the state events below. Enemy voices come from `Core/EnemyVoices.cs`: the game has no sound field in the enemy data block, so the family is read from the block's name and mapped to `AK.EVENTS` names found in the game's event list (a family without its own event, and an unknown name, use `ENEMYVOICE*` / `ENEMYDETECTIONSCREAM`). A death is reported by the timeline before the enemy is forgotten, so its family and last place are still known; a hurt voice plays at most once per enemy per 400 ms. A lost custom limb (EnemyLimb) is shown on the enemy's puppet through ForgeCore `EnemyPuppet.DestroyLimb`, the limb's own `DestroyLimb` that a client runs on the destroy packet (no damage); `WorldState.LimbsGone` keeps the lost limbs per living enemy (ids 0 to 63) and `Puppeteer` matches every puppet to it each frame, destroying missing limbs without the destroy effect and replacing a puppet that shows a limb the recording has not lost yet (a jump back). A sentry shot shows the third-person rifle muzzle flash at the recorded gun place; when the next event is a bullet hurt at the same moment, the tracer (`Fx.Tracer`) runs to that limb of the enemy's puppet, else there is no tracer (the recording has no direction); no fire sound, since the sentry's weapon audio data block is not recorded. Scout feelers post `SCOUT_FEELERS_OUT` / `SCOUT_FEELERS_IN` at the scout; the tendrils themselves are not shown (the game makes them only through `ScoutAntennaDetection`, which runs detection). A player going down posts `PLAYER_DOWNED_1ST_PERSON` when the eye view shows that player; `AK.EVENTS` has no third-person downed event (the `TEAMMATES_DOWN_*` events are music). Not presented: the game's explosive-mine sound (ForgeAudio documents it stays silent when posted by name), the sentry fire sound, a wave's contents, noise, light modes. `Jumped` keeps one rule for every lasting thing: `ReplaySounds.StopAll`, then every level object the recording has touched (`Touched`) is set to its state at the target moment or, before its first event, to the level's first state; the alarm's and scan's lasting sounds are the game handler's and follow the state; `Deployables.Restore` does the same for sentries, mines and foam. Sounds the game's own handlers post are not in the speed tiers.

`Native/Playback/Deployables.cs` holds what players put down, as the game's own objects with their logic off: a sentry is the owner's tool line through `Gear.SpawnSentry` (`enabled` false, turned by `UpdateRotation` and fired by `FireBullet(false, false)` from the recorded shots), a mine `Items.Spawn` in `ItemMode.Instance` (detection off, trip line laid by one raycast with the laser's own scan mask), foam `DoFireGlue`, `DoSpawnGlueStatic`, `SyncIncomingMerge`, `DoDestroyGlue` with the projectile's own `CollisionCheck` and `OnTriggerEnter` skipped while a replay runs. The presenter calls `Note`, a jump `Restore(state)`, `Puppeteer.Sync` calls `Frame`. Alarm sound: `ChainedPuzzleInstance.OnStateChange` as a recall posts the data block's `AlarmSoundStart` / `AlarmSoundStop`, `CP_Bioscan_Core.OnSyncStateChange` the box, counter and (not as a drop-in) complete events with `PARTICIPANT_COUNTER` from the players it is given. Music: the drama machine is off once a Music event comes, and `MusicMachine.ChangeState` plays the recorded state. `Puppeteer.LoadoutOf(slot)` is what a player carries at this moment; every slot ever held has a body from the start, renderers off while the slot is empty.

State events change level objects through `EventPresenter.Setter` (`WorldStateSetter.Set(kind, key, near, state, extra, instant)`, objects found by their recorded position; the game side is ForgeCore `WorldStates`). Doors and supply boxes always animate here (WorldStates turns their animators' culling off and evaluates the pose at once for an instant state; a door whose object is off waits in WakeDoors). What the hands hold comes from the state each frame (Carried): the level's own carried item, else a copy of the recorded kit's item. CorpseBook holds the bodies of enemies that died in playback: hidden 15 s later or at any jump. Doors, generators and supply boxes switch through the game's own handler (animation and sound) when the speed tier would play their sound (doors count as key events), else they are set without animation. Scans, alarms (chained puzzles), pickups and the reactor are always set without animation and their sound is posted here: their handlers also run game rules (a solved scan or alarm opens things, a reactor stage starts waves), which a replay must not do. A pickup is matched by position the first time its recorded key comes and kept for that key (`WorldStateSetter`), so one put down elsewhere is placed at the recorded place (`WorldStates.Item` with a place). Items spawned during the level (ItemSpawn) are kept in order in `WorldState.ItemSpawns`; `WorldStateSetter.Spawns` spawns the ones recorded in the pickup mode (`ItemSpawned.IsGroundPickup`) through ForgeCore `Items.Spawn` at the recorded place and hides spawns later than the moment; an item spawned in a hand or as a placed deployable (any other mode) is not put on the ground, since the player's and the deployable's own events show it. An item without a pickup form is refused by `Items.Spawn` and skipped without an error. The Environment state's fog data block id is shown by `EnvironmentView` through ForgeCore `WorldStates.Fog` (`SetFogSettingsLocal`, this game only); while the observer's fog clearing is on nothing is set, and when it is switched off the recorded fog is put back. The recorded light sequence names no zone and no on or off, so no light mode is set. `Jumped(state)` after a seek, and once when the replay starts, forgets what was shown, makes the spawned items match the moment, then sets every level object of those kinds (door, generator, pickup, alarm, scan, supply box, reactor) whose state at the moment differs from the one it last put it in (`EventPresenter.Applied`) and the fog to its recorded state at once (by mid-level a recording has touched 130 to 360 objects, of which a 1 s or 5 s jump changes a median of 0 to 1; setting all of them again ran every door's handler and played the doors of the whole level); a door, lock or supply box set by a jump has any sound its handler posts stopped (`GameVoices.Catch`, then `AudioKit.StopGameEvent`); objects it cannot find near the recorded place are counted and logged once. Lost limbs and item spawns are one-shot events that no keyframe block repeats: the timeline keeps them from every block it has read (`Seek` reads the blocks before its keyframe once if needed) and applies the ones before the keyframe first. Terminal screens (`Playback/Terminals.cs`): the replay level's terminal nearest (3 m) to the place the recording names for a terminal key (`Analysis.TerminalPlaces`, from its TerminalState and Terminal events) shows that terminal's recorded lines, typing and state through ForgeCore `WorldStates.Terminal*`, on this machine only; the screen the level built it with (its start-up text, not recorded) is read when the terminal is first found and stays above the recorded lines. Playing with every sound (up to 2x), a line goes through the game's output queue (its wait, look and print sound), typing through the game's receive handler for another player's typing (a key sound per recorded character), and a state (Sleeping, Awake, PlayerInteracting with the puppet of the recorded user; command states are not shown) through the terminal's receive handler; faster, the terminal is marked and its screen is set once per frame to the moment (`Analysis.TerminalScreenAt`: its last 64 recorded lines and the input line, no sound). A jump sets each terminal's state at the moment with the handler's sounds caught and stopped (`GameVoices.Catch`) and sets the screen to the moment's lines without printing the ones between; a terminal whose screen at the new moment is the one shown (lines printed by then and input line) is left alone.
`Native/Playback/Listening.cs` moves to the view what the game hears from the local player's body: a prefix holds `DramaManager.OnPlayerEnterArea` (0x149C2E0, the room tone `AMBIENCE_LOOP_*`, called only from the local player's `PlayerAgent.set_CourseNode`) during a replay and calls it for the area at the view when that changes (4 times a second, ForgeCore `Level.CourseNodeAt`); a postfix on `EnemyAgent.UpdateSfxLOD` (0x1564DA0, `min(99, distance^0.5)` to the local player) sets `SfxLOD` from the view with the same formula. Both methods are patched by ForgeReplay only. Wwise's listener is the `AkAudioListener` on `FPSCamera`, which the replay moves.


`REPLAY_FILE=<file.frpl> dotnet run --project Mods/ForgeReplay/tools/Dev -c Release` (the development tools over recorded files live in `tools/Dev`, apart from the tests; `REPLAY_NOISE_DIR`, `REPLAY_CALIBRATE_DIR` with `REPLAY_NATIVE_ROWS`, and `REPLAY_RATING_DIR` with `REPLAY_NATIVE_ROWS`, `REPLAY_GAMEDATA` and optional `REPLAY_RATING_TABLE` are theirs too) prints what a recorded file holds: events per type, the header and footer, each player's look pitch every ten seconds (what the eye view shows), the client-side inferences (`Core/ClientInference.cs`) against the host's exact values, the automatic camera's switches over the file, and a hard-kill check (the file cut at nine places must list as incomplete and play to its last whole block), then samples per entity.

What is exact and what is worked out, per statistic (`Analysis`, `ReplayFeed.Cell`; a ~ only on a non-zero number with a worked-out part, `PlayerStats.EstimatedKinds`): hits: kind 2 rays for the recorder, the host's own and bots' shots from its 112 records (a hit when the ray ended on an enemy limb), settled bullets near the player's shots for others on the host (`BulletHits`, capped at the rays), a ~ for others on a client without them. Damage taken: exact where PlayerHurt exists (`HurtExact`: the recorder, the host's bots), else the health bar. Revives given: ReviveBy, exact everywhere. Packs used: the count in PlayerKit going down (or gone just after a use motion; dropping it empties the slot too), exact everywhere, and a host's 110 record settles that a host player's or bot's use was a use. Supplies received: Supply events; a host's 109 record adds the gifts the host's machine made (its own player and the bots), and a gift from another client is inferred. Player hurt sources (down causes, friendly fire): PlayerHurt where this machine settled it, and a host's 111 record for the host player's and bots' hits. Enemies woken, host: the player the Wake event names, a propagated wake-up credited to the waker of the enemy that passed it on; in an older host recording the one player at the distance the game woke the enemy at (within 1.5 m); on a client inferred. Mines laid: the mine's owner in the state's extra (`Item.Owner`, slot + 1), else inferred. Tongues dodged: the recorded target who lost no health and was not caught; exact for the host and the recorder's row. Explosive damage: the owner of the mine that went off within 500 ms. Damage and kills: the health the hits took off (settled EnemyHurt) and the hit that took the last, on the host exact for everyone. Weak spot hits and backstabs: settled bullets and swings on the host, the recorder's own readings on a client (`HitsKnown`); a client is not told where another player's hit struck, so their cells are empty.

`Core/ClientInference.cs` fills the rows of PLAN 5.6 from the samples and the events every machine sees, never from the host-only ones (PlayerHurt, Pack, Wake, EnemyHurt), so running it on a host recording gives each inference's error against the host's exact value: damage taken from the drop of a player's health byte (a share of full health; the attack, tongue, projectile or explosion nearest in time and reach is the source), what woke a sleeping enemy, a mine's owner (the player who made the place motion within 6 m in the six seconds before), a pack (a give is matched to another player whose ammunition rose or infection fell, a self use to the user's own rise), a tongue that went back without costing the player it reached for any health or catching them (a dodge) and the reviver (the nearest teammate within 3 m who is not down). `Analysis.Run` runs it in the same pass as the counts (samples too) and settles health drops and wake-ups at the end (`Finish`), so the events just after a drop or a wake-up count; each looks only at the slice of its time window in its time-ordered list, widened by the most the feed ever went back in time (1 ms in the 11-06 recordings), with the same edges and order as a scan of every entry (`InferenceChecks` checks both against each other and an edge moved by 1 ms); its results become `StatDelta`s like the exact counts, so `StatsClock` follows them with the clock. They are not in the footer (the recorder feeds `Analysis` events only); the list's details read the whole file once for every recording. `Core/ReplayFeed.cs` turns a row into a cell (`ReplayFeed.Cell`: text with ~ or —, and its quality) for the panel and the list alike; the damage taken read off a health bar is the share times the game's full health (`PlayerDataBlock` 1 `health`, read in `ReplayScreen.FullHealth`), empty when that cannot be read. In recordings without PlayerKit events packs are exact only for slots with their own Pack events (the recorder's: the hook is `ResourcePackFirstPerson`, the local player's), the rest are matched. Enums read from the game's interop: `pGenericInteractAnimation.TypeEnum` PlaceTripmine 0, GiveResource 5, ConsumeResource 6; `PlayerLocomotion.PLOC_State` Run 2, Jump 3, Land 5, Downed 7, GrabbedByTrap 12, GrabbedByTank 13, GrabbedByPouncer 16; `eDoorStatus` Open 10, Destroyed 11, Opening 16; `EnemyAlert` Sleeping 1, Awake 2.

Noise (PLAN 5.6). `Core/NoiseRebuild.cs` reads the player actions: a locomotion change to run, jump or land (PlayerStatus), a shot (a shotgun's pellets in the same millisecond are one), a swing, and a door going to open or destroyed with a player within 4 m. The game gives these actions no radius: a sleeping enemy hears a walk, run, jump or landing inside its `EnemyDetectionDataBlock.movementDetectionDistance` and a shot inside the gunfire distance (`weaponDetectionDistanceMax`, narrowed towards `Min` by node distance, which a recording does not hold, so the far end is used) — ForgeCore `PlayerNoise` and ForgeEnemy `EnemyModule.Wake` document the game's check. `Analysis.Run(..., hearing)` gives those two distances by enemy data block (`ReplayScreen.HearingOf`, through `EnemyDataBlock.DetectionDataId`). A wake-up's candidates are the recorded Noise events that cover the enemy, the rebuilt actions inside the enemy type's distance in the 3 s before to 0.2 s after, and every player running inside its movement distance at that moment; the nearest in time is the source, another player's candidate within 250 ms leaves it empty. The radii could not be read off recordings: `REPLAY_NOISE_DIR=<the game's replay folder>` sets every host recording's Noise events against these actions, and in the nine host recordings of format 3 on 2026-11-02 (157 Noise events) every event had no source slot (the game's `NoiseManager` noises' maker is not a player agent) and only 5 of 582 shots and 4 of 374 swings fell within 150 ms and 3 m of one, by chance of place. A melee hit, a door opening and a door breaking have no hearing distance in the game data, and the attenuation range of their sound events is not readable here (the website's audio catalog holds clips and event ids only; the Wwise banks were not parsed), so `NoiseRebuild.Reach` estimates them from the like sound: a melee hit and an opening door as loud as a run (`movementDetectionDistance`), a broken door as loud as a shot (`weaponDetectionDistanceMax`). A wake-up credited through them is an estimate (marked ~, explained in the i icon). A scream wakes enemies for no player, so its range has no effect on a player's statistics and is not modelled. `REPLAY_GAMEDATA=<folder with Enemy.json, EnemyDetection.json, Player.json>` (the website's copy: `Web/public/data/maps/game`) gives the file dump the same distances and the full health, and the dump compares the wake sources with the host's Wake events (not propagated, one player at the recorded distance) and the damage taken with the host's PlayerHurt.

Joins and leaves: a Presence event may carry, after slot and joined, the player's name and loadout (Text, Text; the loadout is the header's gear JSON lines). `Analysis.Presence` keeps them; `ReplayFeed.Holder` gives a slot's holder at a moment (the header's player until the slot's first Presence line, then the newest line: a join with its own name and loadout or the header's when it carries none, a leave an empty slot). The screen remakes its cards only when a Presence line is passed; kill feed, bar marks and chat lines take the name as of their own moment; the statistics have a column for every slot held at any moment.

ForgeDevelopment's `LevelScenario` plays a fight and a round of level interactions without anyone playing, for 120 seconds from a few seconds after it is started, through the game's own calls and never key presses: strikers, a tank, shooters and a sleeping group, the wielded gun and the melee weapon, a walk, a run, crouch and jump, throws, chat (`PlayerChatManager.PostChatMessageLocaly`), noise (needs the player's course node), a marker ping (the game's `ManualPingTarget`), the tool slot's sentry (`Gear.SpawnSentry`) or mine (`ItemReplicationManager.SpawnGear`), a resource pack taken in the hands and applied, down and revive, a supply box, security door, reactor start-up, chained puzzle, generator, pickup, terminal command, survival wave, an item spawn and a checkpoint stored (`CheckpointManager.StoreCheckpoint`, then the buffer capture) and reloaded (the replicated reload interaction), the same calls ForgeDevelopment's pack test makes. A step the level cannot supply fails with a log line (`scenario: FAILED reactor start-up: no reactor in the level`), so pick a level with a reactor and a stand-alone generator: `SeededDrop Start 37-B1` (R4B1: a reactor and a generator at a cell-locked door). A level whose generators all belong to a generator cluster (38-C2) has the cluster but no generator in the scene until its objective places them. Steps that need the game ready first (the two reloads wait for a gun in the hands, the gun is wielded again a second before the second one) are tried each frame for a few seconds and then fail with what they saw. `LevelScenario Start true` leaves the level up and recording after the scenario (otherwise it leaves the level and the recording is closed), so the game process can be ended from outside to test a cut-off recording.


## Puppets (playback)

Native/Puppeteer.cs is the only place that makes puppets; Replayer.Late (registered with Frame.OnLateUpdate, so it runs after the game's animation) calls Puppeteer.Sync each frame. Enemies: one EnemyPuppet (ForgeCore Puppets.Enemy) per recorded enemy within 70 m of the followed player and in the dimension that player is in (an arena enemy at overlapping coordinates is not shown in reality), at most 4 spawned per frame, parked (agent hidden, puppet kept) beyond 100 m and shown again inside 70 m; an enemy's puppet ends at its end event (Puppeteer.EnemyEnded): killed through the game's own death (Die) when the event says it died, else hidden for good. It must end there and not at the next placement: the recorder numbers enemies by the game's enemy slot, and the next enemy in a freed slot (a wave fills them at once) comes with the same number in the same frame, so a puppet kept until the next placement was driven to the new enemy's place (the 14.8 m puppet error at a mass spawn). A puppet's own state changes (an action, back to walking) put its hold back at once (ForgeCore `EnemyPuppet.Rehold`), so the state's own entry code switching the AI, the nav mesh agent or root motion is not counted as the game taking it back; a real take-back logs which of the four changed and in which state. Placing: `WorldState.Place` interpolates from an entity's latest sample to the next one (`Timeline.FindNext`, which looks up to `MaxStepMs` 250 ms ahead, into the next block when it must, and stops at the entity's `EnemyGone`); with no next sample in that time the entity stood still and is held, because an unchanged sample is not written. An enemy's walk animation input is the speed from its latest sample to the next (zero with no next one), smoothed over 0.12 s. A player's is the recorded PlayerMotion, which `PlayerLocomotion.UpdateFullBodyAnimValue` moves towards at the game's own 7.5 per second (`CosmeticPlayer` at the same rate). Players: the replay level opens bot slots (Puppets.OpenBotSlots, one per recorded player, at most 3, the recorder first) and each recorded player drives one bot's player agent; stance (crouch) and the wielded slot come from the latest PlayerStatus. The local player is the observer and has no model; a fourth recorded player is drawn as a `CosmeticPlayer` (below). The body copy plays an interact, throw or melee state only from `CosmeticPlayer.Actions`, which stays empty until the numbers are read from a remote player's body: while recording, `AnimatorStateProbe` writes every state change of other players' bodies and every interact, throw, reload and melee event to `replay/animator-states.log` (config `Recording/LogRemoteAnimatorStates`, on by default; 20000 lines per recording).

Actions: ForgeCore's `EnemyPuppet.Attack`, `Hitreact` and `Scream` put the enemy in the game's own state (the one a client puts a remote enemy in) and hand it the recorded data through the receive entries (`RecieveAttackStart`, `RecieveStateData`, `OnStateShouldBeActivated`); the puppet goes back to walking after the recorded time. `PlayerPuppet.Interact`, `Throw` and `MuzzleFlash` are the remote-player entries (`PlayerInventorySynced.SyncGenericInteract`, `SyncThrowState`, the weapon's own muzzle flash), `State` enters jump, fall, land, downed, at a terminal, a tank's tentacle and the nearest ladder (a trap's and a pouncer's hold are not entered: those states read a holder the replay does not have). `MeleeSwing` swings the recorded player's third-person weapon, whose own code plays the swing sound, so the presenter posts one only for a player with no puppet. An enemy's pose comes from `WorldState.EnemyLocomotion` each frame (`EnemyPuppet.Stance`), so a jump lands in it without any event.

Screen, `Native/UI/ReplayScreen.cs`: name tags and pings are drawn by the replay over the picture from the camera's view (the game's own are hidden with its HUD, and only someone in the game at this moment gets a tag); the game's log lines (not type 1, chat) top middle; the objectives from the recorded layer states with their text from the level's data block; the events list is the time bar's marks. The followed player at a terminal gets the terminal's printed lines and what is typed in a panel (`Analysis.TerminalTexts`, not on the terminal's own screen: a recorded line has no place, only an instance id of another run). The objective timer and reactor text stand under the objectives, the zone on the card. `Analysis.GameLines` (with warden intel) and `Analysis.Pings` hold what these read. Above 4x `AudioKit.SilenceGame` holds the game's handlers' sounds too (PLAN 5.3).

What is thrown (`Deployables.World`, from `ReplayExtras.ThrownNow`) is the game's own item, placed by the recording with no physics and no contact, a glowstick's life is held so it does not despawn itself and a fog sphere is compared with its recorded state every frame, because the item resets it on its first frame; zone lights go through `WorldStates.ZoneLights` when the recorded map changes; both read the state each frame, so a jump needs nothing of its own. Voice lines go to the puppet's own voice, so the voice is the bot's character: `Puppeteer.FreeBot` gives a recorded slot the bot sitting in the same game slot (the observer's slot has none, so that recorded player is a body copy, which says its lines with its own recorded slot's character switch), and only a bot no other recorded slot waits for otherwise. Aiming (108) drives `FPItemHolder.ItemAimTrigger` where the recording has it, the recorder's own player only.

## First person (Native/Playback/FirstPerson.cs)

The view is the screen camera's eyes mode (`ReplayCamera.Eyes`; `ReplayCamera.Place` calls `FirstPerson.Frame` with the eye it placed, so there is one eye position). That eye is the watched player's recorded feet, recorded look turn and the height of its recorded stance (`Agent.Position` + `ReplayView.EyeHeight`), for the recorder and for everyone else alike; nothing of the eye is recorded. The local player's own first-person arms and gun are the picture: a subscription to `GameHooks.FirstPersonHolderLateUpdate` moves the `FirstPersonItemHolder` to that eye and look direction after the game placed it (the observer's body never moves). `WantsToWieldSlot` follows the recorded wielded slot, and the viewed player's four gear lines of the file header (standard, special, melee, tool) are equipped with `Gear.EquipLocal`, every line whose parts are loaded at once (the one in the hands first), each missing line checked every frame; only the slot in the hands is wielded again after its item was replaced. Recorded events play the game's own animations of the item in the hands, animation only: a shot `TriggerFireAnimationSequence` and the weapon's muzzle flash, a reload `TryTriggerReloadAnimationSequence`, a swing `MeleeWeaponFirstPerson.ChangeState` (light alternates `AttackMissLeft` / `AttackMissRight`, heavy is the released charge, push is `Push`; a `Skip` subscription to ForgeCore `GameHooks.MeleeAttackDamage` (`MeleeWeaponFirstPerson.DoAttackDamage`) keeps the hit from being dealt while the eyes mode is on, so a swing never hurts what stands in front of the camera), placing a mine and a shove through `Interact`. The recorded stance and speed (the puppet's smoothed velocity, 0.3 and 3.2 m/s) start the holder's `OnIdleStart` / `OnWalkStart` / `OnRunStart` sway and set its `WalkInertia` / `RunInertia` (the 0..1 targets its walk and run weights ease to in `UpdateCommonWeights`, left at rest by the observer's own locomotion) every frame and again after the holder's update, and the viewed player's turn between two frames (yaw and pitch in degrees, none across a jump) is written as the observer camera's `m_lookInputMouse`, the mouse part of `LastLookInput` that the holder's `UpdateLookSway` pushes the arms by, and a recorded jump or landing `PlayJumpAnimation` / `PlayLandAnimation`, because the local player's own locomotion never moves. Leaving the eyes mode hides the arms again; the replay ends in the menu, which rebuilds the observer's real gear. Number keys, V and the cards belong to `ReplayCamera`. Not played: the progress of a reload or a tool use beyond what the recording holds (the start of each), and tool animations of items without a fire sequence.
## Member rating (Core/MemberRating.cs, Core/RadarGeometry.cs, Native/UI/RatingStore.cs, Native/UI/RadarChart.cs)

Rating a member (PLAN 6) takes numbers the statistics already hold; nothing is recorded for it. `MemberValues.Read(analysis, slot, durationMs, fullHealth)` makes one number per `RatingMetrics.All` (a rate per minute of the recording, except `weakShare`), null where the recording does not say, and marks worked-out ones with the same exact / estimate / empty test the statistics use (`ReplayFeed.Cell`). Dimensions in drawing order: `output` (`damagePerMinute`), `kills` (`killsPerMinute`), `accuracy` (`weakShare`, weak hits over landed hits: the recorder, the host, or a client whose host records are in force), `survival` (`takenPerMinute`, `downsPerMinute`, both lower is better), `support` (`rescuesPerMinute`, `gavePerMinute`, the latter the recorder, the host, or a client with the host's records in force), `mission` (`interactionsPerMinute`: terminals used, scans stood in, doors opened). Every number is placed between its two fixed anchors by `RatingTable.Score`; a dimension is the mean of its known numbers' scores, the total is the mean of the known dimensions, and `rating.forge`'s 15-band grade table cuts the total. A dimension with no number is left empty; fewer than `minDimensions` known dimensions is `TooFewDimensions` (no grade). `RatingStore` does not rate a recording shorter than `minSeconds`.

`Mods/ForgeReplay/rating.forge` ships with the plugin (beside the DLL; `package_release.py` includes it). `RatingTable.Parse` refuses a file that is not exactly this shape (it logs once and nothing is rated):

```json
{ "schemaVersion": "1.0.0", "minSeconds": 120, "minDimensions": 3,
  "grades": [ { "name": "S+", "from": 0.97 }, ..., { "name": "D-", "from": 0 } ],
  "metrics": { "damagePerMinute": { "owner": 165.1626, "low": 38.8297 }, ... } }
```

`schemaVersion` is `ForgeCore.FormatVersion.Current` (a string). `grades` run best first, `from` falling to 0 (a score at or above it earns the grade). `metrics` names every `RatingMetrics.All` key and no other; each is `{ "owner": number, "low": number }`, two different numbers with the owner above the low for a higher-is-better number and below it for a lower-is-better one. A value at the low anchor scores 0.14 (D), at the owner anchor 0.91 (S-); the owner's better run and any better play reach S and S+ (up to 1), anything below the low anchor is D-. The bands are interpolated from those two anchors, not from any distribution of other players. The owner anchor is the owner's weaker value over the two vanilla ALT://Rundown 3.0 D1 recordings (`20261109-154432_34-D1.frpl` and `20261109-155621_34-D1.frpl`, recorder `NAinfini`); the low anchor is the weakest teammate value in the same two runs. Teammates' weak hits and packs given are not in a client recording, so those two low anchors are estimates (0.05 and 0); the bands between the two anchors are estimates to be tuned.

`member-ratings.json` in the replay folder (`RatingCache`; not a Forge format, derived, safe to delete) keeps per recording file name its fingerprint (length and write time), duration and each member's numbers, so the list rates a recording without reading it. `ReplayList` adds the recordings it has not read (finished ones, read once each through the same background read as a client row's kills) and `RatingStore.Flush` writes the file when the reads stop; entries of recordings deleted since stay (up to 500). It decides no grade and holds no points for `rating.forge`; that file alone does.

`REPLAY_RATING_DIR=<folder of .frpl> REPLAY_NATIVE_ROWS=Web/public/data/catalogs/vanilla-values-native.json REPLAY_GAMEDATA=Web/public/data/maps/game [REPLAY_RATING_TABLE=Mods/ForgeReplay/rating.forge]` runs the same reader and `MemberValues` over every recording in the folder and prints each member's numbers (a worked-out one prefixed with `~`), the six dimension values, and with the table the dimension scores and grade. The anchors in `rating.forge` were computed from its output for the two D1 recordings; it is also how a later tuning pass checks a changed table.

`RadarChart` draws a star radar on a `HudCanvas` from scores alone (0 to 1, NaN for an empty axis): grid, any number of polygons (filled translucent or outline only, each with its own outline width), labels. A polygon's fill is a sprite made from `RadarGeometry.Fill` the first time it is wanted filled with those scores; picking another player on the rating page only flips which polygon is filled, so nothing is made again and a frame allocates nothing.

- `Skipped` (Native/Playback/Skipped.cs): playback is best effort. What this game cannot restore (an enemy type it does not have, an item, gear, terminal or level object missing or elsewhere, an event that throws) is skipped and the replay plays on; a missing enemy type is remembered so it is not asked of the game every frame (`Puppeteer`), and an object that was never made is not touched by its later events (each presenter keeps its own failed state). Each different thing counts once (`Skipped.Note(reason, example)`), the first of each reason goes to the log at once with its example, every reason with its count when the replay ends (`Replayer.Stop`), and the screen pushes a quiet warning notice with the count (`toast.skipped`) at most every 20 s while it grows.
- `EnemyMarks`: ForgeVisual's automatic enemy outline reads the game's AI mode, which `Puppets` sets off, so it draws no puppet; instead ForgeVisual's own selection (`EnemyOutlineTracker`, the recording's entities as its slots and a puppet's instance id as the generation: within the library style's 35 m, in front of the camera, the nearest first, at most 24) picks among the puppets (`Puppeteer.Visible`), and the picked ones get `Outlines.Add` (not X-ray: only where the camera sees them, PLAN 5.4) in the recorded alert settled against the recorded locomotion (ForgeCore `EnemyAlerts.Settle`: a client's AI mode stays asleep for seconds after the wake-up, 11-06 median 2.2 s, and sometimes for good; low two bits of the sample state: asleep in the HUD text colour, awake in the warning, hunting in the red, the library style's opacities), checked five times a second and added again only when an enemy's state or puppet changed.
- Positions: puppets and the camera read `WorldState.Shown` (`Core/Timeline.cs`), `Place` eased with Unity's SmoothDamp over `SmoothSeconds` (0.06 s) of recording time, taken at once beyond `SnapMeters` (2 m), after a gap over 250 ms or a time going back, and started afresh by `Clear` (every jump); the same time twice gives the same answer, so the puppets and the camera agree. `Place` stays the raw line for everything else (statistics, focus, distances). Paused (`Replayer.Freeze`), `Time.timeScale` is 0 and Wwise is suspended (`AkSoundEngine.Suspend(false)`, `WakeupFromSuspend` on play and on `Stop`); not while preparing. A jump calls `Puppeteer.Jumped` (ForgeCore `EnemyPuppet.Settle` and each held agent's `Sound.Stop()`), `ReplayCamera.Snap` (no easing across the level) and clears the particles of every playing `ParticleSystem` (at most every 0.2 s, once after the last jump). The list (`ReplayList.CanStart`) has a play button only on the main menu or in a lobby with no replay playing or starting.
- `ReplayCamera`: two states. Watching: the mouse turns the free camera (read with `InputLease.Axis`, the system cursor stays locked), W A S D fly, E up, Q down, Shift four times faster, the wheel sets the speed (1.5 to 48 m/s, ×1.25 a notch), and flying eases in and out (exponential, rate 12); behind a player the mouse circles the player (in `Follow` the circle turns with the player's heading, eased; in `Orbit`, the first view of a replay, only the mouse turns it; pitch -35 to +60 degrees above the 8 degree default) and the wheel sets the distance (1.5 to 8 m). The wheel works the same while using the screen. Using the screen: Control held, or tapped (under 0.25 s) to stay until tapped again (ForgeUI `HudPointer.Toggle`, enabled while the replay plays); the HUD pointer shows, the view stays still and the time bar, cards and buttons take clicks. Views (`ViewMode`, choices in `Core/ReplayView`; left click (not while the pointer is on the screen's controls, `ReplayScreen.PointerOnHud`), V and the camera button go round `Orbit`, `Follow`, eyes, free (`ReplayView.NextPersonView`; above goes back to `Orbit`); the automatic camera only chooses the player, `Director.MinStayMs` 12 s): free; behind a player (0.45 m up, stopped short of walls by a 0.2 m sphere cast on `LayerManager.MASK_WORLD`, the stop coming in fast and going back out slowly, and the way the camera looks not depending on it); the player's eyes (its recorded feet and look turn at the height of its recorded stance; the game's own near clip, with the first-person arms and gun, see First person); above the player (6 to 60 m, the wheel). The screen camera's lease is the only one Replay holds: the game's own camera keeps the pose `ReplayCamera.Look` gives it, so the eyes view can never be left to a third-person placement. A new view or player glides there over 0.45 s (smoothstep of position and turn) unless the camera would travel 25 m or more, which cuts. Keys: every one is a ForgeUI key action (`Native/UI/ReplayKeys.cs`, table below), so the player rebinds it in the game's settings; free flight reads the game's own move axes (`InputLease.Axis(MoveHorizontal / MoveVertical)`), so a key changed in the game's settings flies too, and E, Q and Shift are read whatever modifiers are held (`ReplayKeys.HeldAnyModifiers`: a chord matches only with exactly its modifiers). The mouse buttons count only while watching or off the screen's controls (`ReplayScreen.PointerOnHud`). A player choice turns the automatic camera off; the middle button goes back to orbiting the watched player from behind at the first distance. Right held plays at 4x and on release puts back the speed and pause it had; left held jumps back 5 s every quarter second. It has its own `CameraLease` (newer than the replay's, so it owns the view) and an `InputLease` holding the game's look, movement, weapon and tool keys off; it places the camera in a `Frame.OnLateUpdate` step after the replay's own, with unscaled time, so the free camera moves while paused. The glide is the replay's own: ForgeCore's `CameraLease` has no blending yet (its plan's C7).
- `ReplayKeys` (group REPLAY, context `replay`, `ui.TakeGameInput("replay")` because the camera's `InputLease` holds the game's keys off during a replay, so these show no conflict with the game's keys). Defaults, mode Press unless said: CameraNext Mouse0 (next view, watching), CameraNextKey V, PlayerNext Mouse1, PlayerPrevious Shift+Mouse1, PlayerPreviousKey `[`, PlayerNextKey `]`, Watch1–4 1–4 (the same player again swaps behind and eyes), Auto 0, Free F, Above T, Reset Mouse2, Play Space, Back / Forward LeftArrow / RightArrow (Tap: ±5 s on the key coming up), Rewind / FastForward the same keys (Hold), PreviousMark / NextMark Shift+LeftArrow / Shift+RightArrow, MarkBack / MarkForward Mouse3 / Mouse4, Faster / Slower UpArrow / DownArrow, FrameBack / FrameForward Comma / Period, ToStart / ToEnd Home / End, Scores Tab (held), Chat Return (opens the chat log and uses the screen), Help Slash, HideUi F1, Rise E, Sink Q, Fast LeftShift, Close Escape (tap / hold 1 s, timed by `ReplayScreen`). Ctrl stays ForgeUI's `HudPointer.Toggle`. Texts `keys.group` and `keys.<name in lower case>`.
- Needs from `Replayer`: `Clock`, `Track`, `Report`, `Follow`, `Pending`, `Active`, `Jump`. `Replayer` reads no keys of its own; every playback key belongs to these controls.
## Observer and view helpers (Native/Observer.cs, Native/UI/ReplayAssist.cs)

- Observer: the local player during a replay is untouchable. PlayerManager.WantToSetGodMode(true, true), ForgeCore PlayerHits.Redirect (every hit 0) and PlayerHits.GateInfection (no infection write); Observer.Sweep (every 30 frames from Replayer.Late) takes out any living enemy that is not a puppet through its replicator's `Despawn` (switched off only where it has none: a switched-off enemy stays in the culling system's nodes and lights, where its shadow is still drawn). The game's own win check is kept from running while the observer is on (a `Skip` subscription to ForgeCore `GameHooks.ExpeditionSuccessCheck`, which answers not won), so items and objectives the replay sets never end the level; ForgeReplay patches no game method for it. Left again in Replayer.Stop.
- Load time: `Session.WatchReplayLoad` (every frame) times a replay load from play being chosen (`Replayer.Pending` set) to the game building the level (`Generating`) and to the level being entered (`InLevel`). The decisions are `LoadWatch` (ReplayCore, timed by the caller). A quick load that ends in the level writes nothing. A slow load writes to the ForgeReplay log, as an error, once when 60 s have passed without the level being entered (with the time until the build started, or that it never started, and the build time so far), and once more when it is entered. A load that ends without the level entered (the chosen replay is dropped by the level cleanup first) writes its stage times once, however long it took.
- Puppeteer.Sync takes a focus point: the free camera's position when the view is free, else the followed player; puppets exist within 70 m of it and are parked beyond 100 m. Puppeteer.HideViewed(slot) turns the renderers of the viewed player's puppet off while the view is the eyes (re-read every 30 frames); -1 restores them.
- ReplayAssist: clear fog reads the volume's density each frame (`PreLitVolume.Current`, the even density and the height boost `m_densityHeightMaxBoost`; a level's fog steps can be height fog only) and, while either is above zero, asks ForgeCore `WorldStates.ClearFog()` (the game's no-density fog block, at most once a second) and restores through `WorldStates.LevelFog()`; global brightness holds a ForgeVisual `Ambient.Lease` (white, strength 0.2, range 64 m), `Follow`s the camera each frame and `Release`s on off, so the library restores strength, range, colour and place and gives up any field another writer changed. Teammates are outlined through walls with ForgeVisual `Outlines.Add(..., xRay: true)` in the game's player colours (redone when a puppet's wielded item changes); enemies by `EnemyMarks`.
- `Director`: a marker of a place (door, alarm, scan, terminal, reactor) belongs to the player nearest to it within 30 m (`Marker.Near`); weights down 8, revive 6, alarm 5, scan and reactor 4, kill 3, terminal 2, door and chat 1. `Analysis.Run(timeline, exact, recorder, notable, hearing)` marks a kill on the bar only when `notable(enemy data id)` (game `EnemyDataBlock.EnemyType >= Special`). When a replay starts, `Replayer.Analyse` runs it on a worker thread over a `FileStream` and `Timeline` of its own (the playback's stream position is never shared), with `notable` and `hearing` read for every `EnemyDataBlock` into plain tables on the game thread first; nothing of the replay moves until it is in (`Replayer.Analysed` then sets the replay up as `Entered` used to). `StatsClock` adds `Analysis.Deltas` up to the clock, so the statistics panel follows the time bar.
- `CosmeticPlayer` (Native/CosmeticPlayer.cs): the fourth recorded player takes no slot. The copy is made 1 s after the bots are held and under an inactive parent, its scripts removed before any wakes; each frame its weapon layers (4 to 8) take the donor's weights and states, except while it or the donor is down. `Puppeteer.SyncPlayers` copies the whole model object the body animator hangs in (`PlayerAgent.AnimatorBody`'s parent: skeleton and meshes) of a bot puppet with `Object.Instantiate`, plus the clothes that hang outside it and are skinned to its bones, re-bound to the copy's own bones (nothing on the copy points at the donor; skinning runs off screen, nothing is forced off, an LOD group shows level 0, one log line says what was copied) when the bots are used up, removes every game script from the copy, and drives its position, yaw and the forward / right / crouch animator floats itself (`MoveBackwardForward`, `MoveLeftRight`, `Crouch`: the game's `PlayerBaseRigController` read from its asset; the game has stripped `Animator.parameters`, so they cannot be listed at run time). It looks like its donor player (the recording names no character), has no wielded item of its own and no jump / down states. Bots stay for the first three because they keep the game's own jump, down and wielded-item animation; moving them to this path waits for an in-game comparison of what the copy loses. The copy's own gear (all built, not yet seen or heard in game): its animator is bound for joint clips through ForgeVisual `Models.BindJoints(Animator, label, out refusal)` (`Playback/ShownPoses.cs`); its voice is a Wwise event posted at its head through ForgeAudio `AudioKit.PostGameEvent(eventId, position, switchGroup, switchValue)` with the game's `CHARACTER` switch of the recorded slot (`CosmeticPlayer.Say`; `EventPresenter` falls back to it when a Say has no puppet), the Say event id being the Wwise event id; its flashlight is a spot light (range 11, angle 40, intensity 0.35, colour 1, 0.963, 0.731: read from the game's `PlayerInventoryBase.m_flashlight`) at the head turned along the recorded look, on while `PlayerKits[slot].Flashlight` says so and off while the player is away (`CosmeticPlayer.Lamp`). Interact, throw and melee swing are not played on it: their animator states are unknown (the input driver could not trigger them), and `Skipped` says so once. Seen in game: four recorded players show four bodies, their clothes and no stray copy; walking and crouching have not been looked at frame by frame.
- First-person items (`FirstPerson.Items`): when the recorded wield is the resource pack, consumable or big-carry slot, the item of the viewed player's `PlayerKit` is stored in the observer's backpack slot with `PlayerBackpack.SpawnAndEquipItem` (the call the game's pickup path ends in: no pickup, no packet, no prompt) and wielded like a gear line; it is cleared with `PlayerBackpackManager.ClearLocalSlot(slot, false, false)` once the recording holds something else, on a change of player and when the eyes mode ends. Nothing is used: the observer's keys are held off by the input lease. An item with no first-person form is noted in `Skipped` and not shown. `Carried` draws the copies for the bodies only. Card, feed and camera-plate weapon names come from `GearTypeNames` (archetype or category public name from the game's data, in the game's language; the loadout's brand name when the data has none).

Keyframe states: `Core/KeyframeStates.cs` is the table of the latest payload of every state event, written again at the start of each keyframe block. A payload that `EventKind.Ends` (foam phase 2, thrown item phase 2, a sentry or mine whose state is not 0) removes its object from the table instead of replacing it, and `Timeline` drops such an object from `WorldState.Objects` / `Extras` the same way, so keyframes carry only what still exists and an object that is absent is gone (the end itself stays in the delta record). Disinfection stations are replayed through ForgeCore `WorldStates.Disinfection` (the game's own `SyncStatusChanged`, nothing else touched); the recorder hook for them is the one on `SyncStatusChanged`.

Statistics of a recording not made by the host: the game does not send a client who dealt a hit. On the host an enemy hit is settled without `ReceiveSetHealth` (a host recording has 0 EnemyHealth), and the three multiplayer client recordings at hand hold none either; where a client does get it, every loss in EnemyHealth is the game's number and `Core/HitMatch.cs` puts it to the players whose hits on that enemy lie in the 1.5 s before it: the recorder's own readings, another player's ray that ended on an enemy limb within 2.5 m of the enemy's place, a swing that landed by the weapon's reach while its damage runs (PLAN 5.5). One player is exact; several share the loss by their hits and the share is a ~; a loss with no hit in the window (a mine, a sentry) is nobody's. The lethal loss names the killer the same way; without any enemy health sync a death goes to the players whose hits lie in the window before it (several: a ~). An enemy no health sync came for keeps the recorder's readings, no more than its full health (`WorldState.Enemies` holds the recorded full health; the timeline reports no spawn to the analysis). Damage taken by the other players: the drops in PlayerHealth, exact.

The other players' damage without that sync: `Core/DamageEstimate.cs`, fed by `Analysis` with what `HitMatch` puts on an enemy and with `DamageData` (`Replayer.DamageTables` copies the Archetype, MeleeArchetype, MeleeAnimationSet, GearCategory, EnemyData, EnemyBalancing and BoosterImplantEffect blocks to plain lookups on the game thread; the melee weapon comes from the loadout's gear category). Formula and rules: PLAN 5.5. `Analysis.EstimatedHits` feeds the deltas and the weapon table; `ReplayFeed.TeamDamage` is the team's sum, used by the list and the export. Calibration: `REPLAY_CALIBRATE_DIR=<folder of .frpl> REPLAY_NATIVE_ROWS=Web/public/data/catalogs/vanilla-values-native.json` feeds the estimate only rays and swings of the recorder and sets it against the recorder's capped readings, with limb shares from the other recordings in the folder: once without any bonus from behind against the readings as older recorders wrote them, once with it against those readings corrected on the hits they flag as from behind. Melee has its own line and a count of swings landed against hits. It also prints on how many enemies killed with the recorder's hits alone the readings fall short of the health, and what the statistics show for a playable file. Files with MeleeHit events: swings count by them, not by reach (`HitMatch.Struck`), and a file with none on an enemy keeps the reach; the calibration has no such file yet. A sentry's and a mine's hits go to the placer (`Analysis.Placed`, `EstimateSentry`, `EstimateBlast`; `DamageData.SentryGun` finds the gun from the recorded fire mode); the calibration has no truth for them, only the count of kills with no hit seen by what lies near them. The website's data copy has no BoosterImplantEffect rows, so the calibration runs without boosters; the game's tables have them. The damage of a recorder's body-limb hits divided by block damage and falloff has a median of 1.00 for four guns up to 34 m (not checked for shotguns: no recorder carried one); falloff's floor of a tenth comes from the game's code as the website's weapon calculator has it, no recorded hit reached it.
